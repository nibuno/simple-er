# SimpleCanvas 使用感レビュー — 2026-10-03

空のキャンバスから非同期通知の構成図を作り、文章編集・配置・保存をブラウザで確認した。**「図と、その理由を同じ場所で考える」という方向性は成立している。一方、文章を入力した直後に図を操作すると入力が消える不具合があり、継続利用の前にここを直したい。**

これはエージェント1体による操作レビューであり、実ユーザーを募集したユーザーテストではない。以下では、実操作で確認した挙動、コードから確認した原因、主観的な評価を分ける。図形が四角形1種類であることは合意された仕様として評価した。

## 実施条件

- 対象：既存の `dist/canvas/`。ビルド・アプリの修正・既存ファイルの編集・コミットは行っていない。
- 操作先：`http://127.0.0.1:8767/`。同じビルドを Python の HTTP サーバーで別ポート配信し、通常版8766・SimpleER側8765には触れていない。
- ブラウザ：macOS上のCodexアプリ内ブラウザ。マウス、ドラッグ、キーボード、UIフィールドへの文字入力を使用。
- 画面：初見操作1280×720、追加確認1440×900、狭幅768×900・375×812。狭幅はviewport変更であり、実機タッチ操作やソフトウェアキーボードは再現していない。
- 先に説明書・実装を読まず、サンプルの観察→新規作成→図とメモの作成→保存メニューまで操作。その後、画面のヘルプ、README、原因に関係するコードを読んだ。
- 作成物：API→Queue→Worker、接続ラベル2本、方針と懸念の独立メモ、Workerの付属メモ、囲み1個。
- ベースHEAD：`07edb963ec87b9a01a36ebea105255aace5cc588`。対象は未コミットの作業ツリーなので、このコミットだけでは再現できない。
- 配信JS：`index-8JGkVyRj.js`（SHA-256 `5241e0e2981decf0a609145ba15763f39475d318dfb73ee3d86c7ce1c903969e`）。CSS：`index-REccTQA_.css`（SHA-256 `ca45cb44bae38f0497a77ba0ff38a793eb96c51bee5edef06987f05c3f8cd743`）。

## 重要度順の指摘

P1は入力内容を失う不具合、P2は保管や図の理解を妨げる問題、P3は小さな操作負担・仕上がりの問題として付けた。

### 1. P1：右パネルで書いた文章が、そのまま箱をドラッグすると消える

**分類：実操作で再現した不具合。**

**手順**：Workerを選ぶ→右側の「メモ」を「ドラッグ直前に書いた検証メモ」に書き換える→入力欄から別の場所へ確定操作をせず、Workerの箱を下へ約104pxドラッグする。

**観察**：ドラッグ前には新しい文章が入力欄にあった。ドラッグ後は元の3行の文章に戻り、ヘッダーは「このブラウザに保存済み」になった。付属メモにも新しい文章は残らない。[入力直前](usability-2026-10-03/08-note-before-drag.jpg)／[ドラッグ後](usability-2026-10-03/09-note-lost-after-drag.jpg)。

別の経路でも再現した。API→Queueのラベルを書き換え、Queue右端の接続点をクリックして次の接続を始めると、新しいラベルが残らない。最初の初見操作に加え、確認用文字列で再現。Escを使わず、既存のQueue→Workerを接続先に選んでから元の線を選び直しても、以前のラベルに戻った。[入力中](usability-2026-10-03/06-label-before.jpg)／[旧ラベルに戻った画面](usability-2026-10-03/07-label-lost.jpg)。

**影響**：「考えを書く→配置を少し直す」という中心的な流れで、書いた内容を失う。入力消失後に保存済み表示へ戻る経路もあるため、単なる確定ボタンの見つけにくさより重い。

**コードで確認したこと**：`Inspector.tsx:43–51` は文章をローカルdraftに保持し、blurで確定する。`Canvas.tsx:311–326` はフォーカス移動でblurを起こした同じイベント中に、更新前の `p.doc` をドラッグ開始時の `before` として保持する。移動プレビューはその `before` から作る（同411行）。接続点は `preventDefault()` し、入力欄の確定を明示的に行わず選択を切り替える（同542–554行、363–368行、`App.tsx:182–187`）。これは観察した二つの消失経路と整合する。

**改善案**：ドラッグ・サイズ変更・接続開始・選択変更の前に、入力中の内容を一度確定する共通処理を置く。ドラッグのスナップショットは確定後の最新ドキュメントから取得する。blurだけに入力保存を依存させない。最小の確認項目は「文章入力→即ドラッグ」と「線ラベル入力→即接続点」の2経路で、移動後・Undo/Redo後・再読み込み後にも文章が残ること。

### 2. P2：「新しいキャンバス」が現在の自動保存を置き換えることを画面から把握しにくい

**分類：仕様上の挙動を実操作で確認した、保存の分かりやすさの問題。**

**手順**：作成した図で「このブラウザに保存済み」を確認→ファイル→新しいキャンバス→再読み込み。

**観察**：新規作成前に、現在の図の保管方法や「自動保存は1枚分」という案内は出なかった。新規作成直後は「元に戻せます」と表示されるが、再読み込み後は空のキャンバスになりUndoが無効になる。画面内に以前の図を開く一覧はない。[新規作成直後](usability-2026-10-03/14-new-canvas.jpg)／[再読み込み後](usability-2026-10-03/15-new-after-reload.jpg)。今回の図は先にJSONへ保存している。

**影響**：「保存済み」を複数の図が保管された状態と受け取ると、別案を始めたあとに前の案へ戻れなくなる。これは誤った保存処理という指摘ではなく、重要な保存範囲がREADMEを読まないと分かりにくいという評価。

**根拠**：READMEの「現在の範囲」では、ブラウザごとに現在の1キャンバスと明記されている（`README.md:51`）。実装も保存キーへの上書き（`App.tsx:295–308`）、履歴の起動時初期化（同66–69行）、新規作成時の置換（同528–534行）になっている。

**改善案**：ファイルメニューに「ブラウザに残るのは現在のキャンバス1枚」と短く明示する。新規作成・読み込み時に前のキャンバスを1世代退避して戻せるようにするか、「現在の図をJSONに保存して新規作成」を提供する。「保存済み」の文言だけに保管範囲の説明を担わせない。

### 3. P2：長い接続ラベルが箱の下へ隠れる

**分類：実操作で再現した表示上の問題。**

**手順**：幅200の箱を「整頓」で横に並べる（保存JSONではAPIとQueueの間隔130）→線ラベルを「注文確定イベント（注文ID・送信先・メッセージ種別を含む）」に変更→Enterで確定→パネルを閉じる。

**観察**：2行に折り返すが、文章の左右がAPI・Queueの箱の下へ入り、全文を読めない。短いラベルでも、初見で手置きした約80pxの間隔では窮屈だった。整頓後の短いラベルは読めた。[長いラベルの欠け](usability-2026-10-03/13-long-label-overlap.jpg)／[短いラベルを整頓した状態](usability-2026-10-03/04-organized-labels.jpg)。

**影響**：イベントの内容・通信条件など、線に理由を付けるほど図の意味が隠れる。パネルでは全文を読めても、図だけを眺めたり共有したりするときに困る。

**コードで確認したこと**：`geometry.ts:161–176` で長い線分の中点をラベル位置にし、空き間隔に関係なく幅200で折り返す。`Canvas.tsx:721–733` はその位置へ複数行を描く。

**改善案**：ラベルの矩形も配置の障害物として扱う。まず線分の空き幅に合わせて折り返し、それでも収まらなければ線の上方など空いた場所へ逃がす。整頓でもラベル幅を間隔へ反映する。単に文字を前面へ出すだけでは箱の文字と衝突する。

### 4. P2：「メモを図に置く」で作成したメモが、編集パネルの外へはみ出す

**分類：実操作に基づく、作成後の見つけやすさの問題。**

**手順**：1280×720で右側にWorkerを置く→右パネルに詳細メモを入力→「メモを図に置く」を押す。

**観察**：選択対象は新しい付属メモになるが、キャンバス右端にその左側だけが見え、本文の大半が見切れた。「全体を表示」を押すと確認できたが、表示倍率は93%から79%へ下がった。[作成直後の画面](usability-2026-10-03/03-attached-note-clipped.jpg)。

**影響**：操作自体は成功していても、置かれた場所と文章の見え方をすぐ確認できず、表示操作が1回増える。すべてを縮小する回避では、他の文章まで小さくなる。

**コードで確認したこと**：付属メモの初期位置は親の右72px（`model.ts:334–355`）。追加後は選択だけ変更する（`App.tsx:805–809`）。`Canvas.tsx:124–155` の表示補正は主にキャンバスのサイズ変化に反応し、既にパネルが開いたままの付属メモ追加では呼ばれない。直接編集の開始には別の補正がある（同162–185行）。

**改善案**：付属メモの新規作成・選択時に、その矩形が見える最小限のパンを行う。可能なら親の箱とメモを両方見せ、倍率を維持する。見える範囲の右に空きがなければ下側を候補にする。

### 5. P3：箱を追加してそのまま書くと「新しい箱」が残る

**分類：追加のキーボード操作で確認した使い勝手の問題。初見パスではフィールドの置換入力を使ったため、その時点では気づかなかった。**

**手順**：空のキャンバスで「箱を追加」→自動でフォーカスされた名前欄に、選択や削除を挟まず「名称テスト」と入力する。

**観察**：「新しい箱名称テスト」になる。既定名は選択されていない。[入力結果](usability-2026-10-03/16-default-title-typing.jpg)。

**影響**：箱を追加するたびに全選択または削除が必要になる。追加後すぐ書ける設計の良さを、小さな操作負担が削る。

**改善案**：新規作成時だけ既定名を全選択するか、初期値を空にして「箱の名前」をplaceholderにする。既存の箱を編集するときは現在のカーソル操作を尊重する。関連：`Inspector.tsx:389–396` の `defaultValue` と `autoFocus`。

### 6. P3：狭幅では「編集中／保存済み」が見えない

**分類：実操作とCSSで確認した情報表示の問題。**

**手順**：768pxまたは375px幅にする→右／下パネルでメモを編集する。

**観察**：1440pxでは見えていたヘッダーの保存状態が消える。375pxでの文章入力・確定・再読み込みは成功したが、編集している最中と保存された状態を画面上で区別できない。[768px](usability-2026-10-03/10-width-768.jpg)／[375pxの入力中](usability-2026-10-03/11-width-375-editing.jpg)／[再読み込み後](usability-2026-10-03/12-width-375-reloaded.jpg)。

**影響**：確定がblurに依存する現在のUIでは、保存されたかを確かめる手がかりが減る。保存失敗や競合時には別の通知実装もあるため、「狭幅ではエラー通知もすべて消える」とは評価していない。

**改善案**：短い「編集中／保存済み」をタイトル行または下部に残す。幅の節約は文言短縮で行い、未確定・保存失敗の状態は常に見えるようにする。原因：`style.css:825–842` で1000px以下の `.save-status` を非表示にしている。

### 7. P3：PNGの日本語折り返しで句点だけが次の行に出る

**分類：書き出した画像で確認した、小さな表示品質の問題。**

**手順**：幅280の「方針と懸念」メモに「確認：監視と手動再実行の担当を決める。」を含む文章を書く→PNGで保存する。

**観察**：キャンバスでは末尾が「る。」の行だったが、PNGでは「。」だけの行になった。文章自体は欠けていない。[キャンバス](usability-2026-10-03/05-restored-desktop.jpg)／[出力PNG](usability-2026-10-03/review-diagram.png)。

**影響・改善案**：共有用の画像で文章の見た目が少し崩れる。`model.ts:91–107` の文字幅推定による折り返しへ、句読点を行頭に置かない処理を加える。画面との完全一致より先に、この短い再現例を直すとよい。SVGも同じ `wrapText` を使う（`export.ts:18–45`）が、別のSVGビューアでの表示比較は行っていない。

## 初見での見つけやすさと良かった点

- 初期サンプルから、箱・通常のメモ・付属メモの役割が分かった。新規作成はファイルメニューから発見できた。[初期画面](usability-2026-10-03/01-initial.jpg)。
- 「箱を追加」のあと図の上で名前と説明を書けるため、作業を始める際にプロパティの一覧を理解する必要がなかった。
- 下部の「余白をダブルクリックでメモ」「Shiftで複数選択」を手がかりに、ヘルプを開く前に文章作成と複数選択ができた。
- 接続元→接続先で線ができ、右パネルが線ラベル用に切り替わる。接続点からの開始も操作できた。
- 「メモを図に置く」は動作を言葉から想像できた。選択後に「箱のメモと連動」「箱を動かすと一緒に移動」と説明され、二重管理への不安を減らしていた。確定済みのメモが箱の移動に付いてくることも確認した。
- 整頓で3箱の流れと間隔が揃い、独立メモは元の場所に残った。囲みは付属メモも含めて作られた。Shift選択と余白の範囲選択の両方を使えた。
- JSONの保存と再読込、SVG・PNG出力が実行できた。日本語の箱名・文章・ラベル、囲み、付属メモを含む小さな図を持ち出せる。
- 375pxではツールバーが折り返され、下部の編集欄から文章を入力できた。主要ボタンが画面外へ消える状態は観察しなかった。

**主観的な評価**：細い線、控えめな緑、面で強調しすぎないメモは、設計の文章を読みながら考える用途に合う。特にメモを付箋風の大きな色面にしないことが、箱と文章の主従を保っている。今回の3箱の検討では図形の種類を増やす必要を感じなかった。四角形のまま、入力の保護と文章配置を改善する方が使用感への効果は大きいと考える。

768pxでは横のパネルが265pxを使い、図の可視領域が503pxになる。375pxの下パネルは短文の追記に使えたが、長時間の設計作業まで快適とはまだ判断できない。狭幅は閲覧・短い追記を中心にする、という方針は検討の余地がある。

## 未確認事項と後片付け

日本語IMEの変換中操作、Windows/Safari/Firefox、実機タッチ・ソフトウェアキーボード、大量要素の性能、複雑な交差配線、別タブ競合、ストレージ容量不足・破損、最大入力長、クリップボードの全経路、スクリーンリーダーの操作は未確認。既存の自動テストは実行していない。READMEにあるテスト成功の記述を、今回実行した結果として扱っていない。

レビュー用8767サーバーはCtrl+Cで終了し、操作したタブを閉じ、viewportの指定を解除した。起動前の接続失敗でできたエラータブ1枚は、ブラウザ側のURL制限で明示的に閉じられなかったため、未保持の一時タブとしてセッション終了時の自動整理に委ねた。通常版のサーバー・タブ・保存内容は操作していない。

次の最小作業は指摘1の入力確定処理の修正と、2経路のブラウザ再検証。図形追加や配色変更より先に、書いた文章を安心して残せる状態にしたい。
